## Windows and Linux candidates

- Windows `0.9.116-alpha.1` never produced a candidate:
  - Run 36285487912 (source `278ff17b`) built the unsigned payload, then
    **skipped** `OIDC-sign, validate, and store exact candidate` and reported
    success. #463 had left `sign` with a flag-only `if`; `unsigned` needs the
    skipped `resolve`, so the implicit `success()` skipped signing. Fixed in
    #467 (`!cancelled() && needs.unsigned.result == 'success'`, asserted by
    `windows-signed-builder-config.test.mjs`).
  - Run 36288408545 (source `427fcafb`) reached the protected sign job, which
    was approved at 08:16Z, and its protected-main recheck refused the source
    because #468 had merged at 03:58Z. Nothing was signed or stored.
- The never-signed entry moved forward as `0.9.117-alpha.1` (windows, linux)
  in #470 with an Orcle-listens paragraph.
- Windows run 36311021151 and Linux run 36311022491 were dispatched for
  `0.9.117-alpha.1` from `297e9617` at 09:58Z.
- Linux run 36311022491 succeeded and stored the private candidate at
  `candidates/linux-alpha/0.9.117-alpha.1/297e9617a2ed44057728225deb440f1e983b1d18/`
  (Neon). It does **not** contain #469 (Linux VAAPI `-bf 0` for every
  session), which merged afterwards; that fix ships in the next Linux
  version rather than a second candidate under the same ID.
- #469 merged at 10:35Z while Windows run 36311021151 waited for sign
  approval, so that run was cancelled before approval (nothing signed or
  stored). #469 only changes the `LinuxVaapi` FFmpeg arguments, so it does
  not change Windows behaviour. Windows run 36313660201 was re-dispatched
  for `0.9.117-alpha.1` from `0c5d5948eb1a13476b549bfa25e576bfe69c2e2f`.
  This record is held until its sign job has run, so `main` does not move
  under it.
